# 页面读取性能工作流

所有页面统一采用测量、定位、改造、验收流程。业务 SQL 保留在所属模块，只抽取已存在重复且语义相同的机制，避免为每个页面新增缓存、线程池或分页框架。

## 1. 固定基线

从浏览器记录真实请求参数、请求依赖和渲染耗时。场景包括默认筛选、空结果、多后端、深分页、详情和不同权限。默认筛选变化时同步更新基准场景。已有 tools/platform/bench_platform.py 是合成数据容量测试，会初始化数据库，不能直接用于生产只读诊断；且未覆盖当前页面全部默认筛选，不能代替页面基线。

比较浏览器加载、公开 HTTP、服务器回环 HTTP、查询函数和 SQL 耗时。记录首次与后续请求、p50/p95、响应大小、并发批次耗时、内存和写入延迟。首次请求不等于冷缓存；小样本 p95 仅作初筛。HTTP 新连接测量需注明 TLS 开销，不代表浏览器复用连接后的耗时。

## 2. 定位与优化顺序

统一 HTTP 测量入口是 tools/platform/bench_reads.py。场景文件是名称到 GET 路径的 JSON 映射，例如 {"health":"/healthz"}，实际测量填入页面真实筛选参数。命令：

    python tools/platform/bench_reads.py --base-url http://127.0.0.1:8100 --scenarios scenarios.json --runs 10

并发对比追加 --concurrency 4。身份从环境变量 AFX_BENCH_TOKEN 读取，报告不输出凭据或正文，禁止重定向。失败请求单独记录并返回非零退出码。首次和后续样本分别报告，每次使用新连接；工具不测浏览器渲染，也不代替结果一致性验证。

定速混合负载使用 --rate 50 --duration 60 --concurrency 12，按场景轮转发起请求。延迟从计划发送时刻计算，包含客户端排队，报告实际完成速率和错误数，避免把发起速率当作吞吐。分别验证预热、不重复筛选和持续写入导致失效的场景；短时结果不能替代长时间容量测试。

公共列表响应复用 ReadCache，通过 main/content 的 read_revision 触发器与查询快照绑定。相关表的写入事务同时更新版本，回滚不会失效；心跳和 token 使用时间不触发失效。此机制仅用于身份无关的用例与问题列表。修改输出依赖时同时检查触发器覆盖，不能套用于权限或随时间自动变化的响应。

使用 Store.open_readonly 读取现有库，不进行迁移。查看 EXPLAIN QUERY PLAN，检查扫描范围、关联次数、临时排序、重复总数计算和逐条补查。trace 回调间隔包含 Python 开销，仅作分段采样；精确 SQL 计时需包含 execute 和完整 fetch。重放与压力测试优先使用一致数据副本。

先减少扫描、无用 JOIN 和重复查询，再检查索引是否匹配实际筛选及排序。列表先选本页 ID，再批量加载展示字段；大日志仅在详情加载。精确总数和页 ID 使用一致快照；排序包含稳定唯一的末级键。不能以更改统计口径换取速度。

## 3. 公共机制的边界

沿用现有职责：Store 管理连接和只读访问，search/result_categories 管理筛选语义，ReadCache 管理缓存容量和并发合并，overview 管理总览只读计算。HTTP 层负责鉴权、参数和响应，不堆业务 SQL。只有明确的重复机制才抽取公共实现。现有代码不全部满足这些目标，逐步迁移并验证。

缓存应复用基础组件，但失效条件按数据依赖确定：

| 数据 | 必须考虑的变化 |
|---|---|
| 总览、执行列表 | 上传、head 更新、重分类、统计重建、筛选条件 |
| 问题列表与详情 | 上述变化，以及领取、续租、关闭、合并、处理标签、验证状态 |
| 知识库 | 发布、编辑、撤回、查询者权限 |
| 运维与配置 | 心跳、时间推进、配置变更、用户身份和可见范围 |
| 能力画像 | 执行数据、特征、比较参数、抽样规则 |

不能将所有接口统一套 ingest_seq。缓存引入前需说明每条相关写路径如何使其失效；状态页没有可靠版本机制时保持实时查询。权限相关响应不能跨用户共享。多进程仅用于已测出的并发 CPU 瓶颈，不能替代 SQL 优化。

## 4. 各页面的基准覆盖

| 页面 | 必测请求 |
|---|---|
| 总览 | totals、pipeline、matrix、perf；默认和组合筛选 |
| 问题发现 | 默认第一页、后续页、深分页、空结果、详情与历史 |
| 修复闭环 | 三个维度、当前/历史关联、状态筛选、详情及轮次 |
| 能力画像 | axes、points、patterns；真实后端与特征 |
| 知识库 | 搜索、分页、详情、不同发布状态和权限 |
| 运维 | summary、efficiency、配置及任务；不同身份与节点规模 |

## 5. 验收与发布

新旧实现读取同一一致快照，以相同参数和身份对照完整 JSON、排序、总数、分页边界、错误行为及权限。缓存需验证写入后立即可见、并发失效和容量。生产数据持续变化时，响应差异不能直接判为回归。

记录单请求与并发的前后指标和执行计划，不能只给热缓存成绩。普通列表可先以代表数据集上回环 p95 小于 200ms 为目标；这是优化目标，不是当前性能承诺。复杂分析请求单独设预算。

按仓库约定在 npussh mlir 加载环境和项目运行时完成相关测试，检查两张 NPU 占用并保留已有任务；仅服务端改动不启动 NPU 工作负载。部署前确认当前实际主机，遵循安装与备份流程，保留回退版本与数据身份。发布后复查回环 HTTP、公开 HTTP、实际页面和写入功能。

每次优化提交说明瓶颈、查询及公共机制变更、结果一致性证据、性能前后对比、缓存失效依据和剩余限制。
