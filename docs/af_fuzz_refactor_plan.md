# AF Fuzz 统一测试平台重构方案

状态：总体方案已获用户同意，进入 D0/D1 首批实施（2026-11-09）。本文是目标设计，不代表当前能力；具体接口与实现须按验收结果确认。开发拆解见 `af_fuzz_development_plan.md`。

评审修订：复现的基础是 seed 对应的稳定生成协议，不是落盘保存用例。CaseBundle 是不可变运行时对象，落盘仅为限额临时缓存/显式诊断导出；在无缓存、无历史数据库的设备上也必须能够重建相同 workload。

## 最新约束修订（2026-11-09）

用户明确采用全新重构，不兼容旧 fuzz 设计、语义和功能。默认接口是 `autofusedbg fuzz replay <数字seed>`，不需 profile 或生成参数。数字内部编码生成版本与随机载荷；一个 seed 同时确定基础样本及动态变体。`--static-only` 只选执行样本，不改变完整用例身份。旧长 token、`--seed-token`、af-fuzz 兼容别名已移除。下文早期兼容要求和旧 token 示例由本修订取代；实现契约见 `af_fuzz_seed_v1.md`。保留历史证据不意味着保留旧对外兼容。

## 1. 背景与目标

当前 `nnsmith_integration` 已经承担用例生成、正确性验证、性能对比、多进程调度、续跑和报告职责，不再只是 NNSmith 适配层。主要问题：

1. 正确性与性能模式各有一套执行和会话逻辑，动态 shape 又产生额外分支。
2. seed 控制随机过程，但尚不能保证所有用例完全复现；已有用户反馈同 seed 广播轴位置变化。
3. 存在 input size 不一致问题，需要区分生成约束冲突、输入绑定错误、重建漂移和后端运行错误。
4. 调度粒度是整个 case，生成、后端编译、设备执行和后处理互相等待。
5. 结果局限于单批；全量 JSON/HTML 重写、下载和浏览器计算随规模增大变慢。
6. 增加 dtype、layout、动态 shape、数值边界等因素时，缺少稳定的公共用例契约。

目标：建立“不可变用例 + 统一执行链 + 资源感知任务调度 + 可查询结果库”。

不以增加更多 worker、拼接 HTML 或重新设置随机种子作为最终解决方案。

### 1.1 成功标准

- 正确性与性能使用同一执行实现；性能只是可选阶段及后处理。
- 所有后端消费内容相同的不可变 workload；仅凭seed独立重建时，所有图与数值决策严格按稳定协议重现，不受设备或运行历史影响。
- 支持多批归档、筛选、配对比较和恢复，重复导入不重复统计。
- case/backend 可以独立调度；CPU 与 NPU 能力允许的阶段流水并行。
- 列表、图表和详情按需查询，不生成包含所有明细的巨大默认 HTML。
- 新因素通过明确的数据契约、生成规则、加载支持和能力声明扩展。

### 1.2 本轮边界

- 重构 Autofuse-Debugger 测试平台，不默认修改 Autofuse 编译算法或 ABI。
- NNSmith 保留为生成适配器，不立即重写求解器和整个算子系统。
- 编译/执行彻底分离可能需要后端接入工作，必须单独验证，不能视为已有能力。
- 生成协议必须长期兼容：既有 seed 的含义不能随工具升级静默变化。协议升级需保留旧实现，并通过自包含 seed 标识选择版本。
- 首期不建设通用分布式集群、多租户平台或任意模型上传执行服务。

## 2. 已知事实与未决问题

### 2.1 当前代码事实

- `generation.py` 被正确性和性能流程共享；编译、比较、会话、错误和产物处理并未完全共享。
- 性能 worker 通过 seed 重建 case，再校验 fingerprint；图、权重和 oracle 被重复生成。
- 动态正确性路径提前返回，没有完整复用静态路径的失败产物和诊断能力。
- 重构前包初始化会设置环境变量并自动应用 NNSmith 补丁；D1 首批已移除该副作用，执行兼容检查默认只读（见 `af_fuzz_d0_evidence.md`）。
- `summary.json` 混合了展示结果、会话配置和 checkpoint；HTML 内嵌明细数据。

### 2.2 前序远端调查结论及限制

环境：`npussh mlir`，Autofuse 在 `~/autofuse`，NNSmith 在 `~/niu/nnsmith`。

- 限定 Add/Mul/ReLU/Neg、float32、小规模配置下，3 个静态用例及 2 个成功生成的动态 workload，其声明 shape 与实际输入一致，重复生成 fingerprint 一致。这只是局部样本证据，不构成整体确定性证明。
- 加载已有 Autofuse overlay 后，一个静态用例 NPU 验证通过。
- 已复现一类动态候选冲突：输入轴变大，固定张量仍为原尺寸，广播约束失效；最终无法生成足够合法变体。尚未确认就是用户报告的 input size 故障。

## 3. 总体架构

```text
CLI / Python API
        |
ExperimentPlan：因素策略、后端矩阵、资源预算、重复次数
        |
生成任务池：自包含 seed 标识 -> 稳定生成协议 -> 完整 CaseSpec
        |
物化与验证：权重、输入、oracle、动态样本、输入约束
        |
CaseBundle：内存中不可变 workload + 内容指纹；落盘缓存可选
        |
任务展开：Case × Backend × 编译配置 × Repeat
        |
资源感知调度器
        |-- CPU 准备 / 编译池 ----> 就绪队列
        |                           |
        |                     NPU 设备租约
        |                           |
        |                     统一执行 Worker
        |                     设备准备 / 正确性 / 可选测量
        |                           |
        |<------ CPU 后处理 <-------|
        |
单写结果服务：轻量 SQLite 结果库（临时文件不归档）
        |-- 本地CLI：运行状态 / 同步积压 / 诊断导出
        `-- 自动增量上传 -> 中心导入 -> 公网Web（默认入口）/ 按需离线快照查看
```

数据依赖方向：入口与编排依赖核心契约；生成器、后端、数据库和报告通过适配接口接入。核心契约不导入 torch、torch_npu 或 nnsmith。

## 4. 核心数据契约

### 4.1 ExperimentPlan：如何组织实验

包含生成因素范围、采样/组合策略、后端列表、ExecutionSpec、EvaluationSpec、CPU/内存/NPU预算、重复次数、保留策略。

区分随机探索、定向回归、固定其他因素的 A/B 对照；不默认对所有因素做笛卡尔积。

### 4.2 CaseSpec：已经决定的测试语义

不是“最大 rank、广播概率”等策略，而是完整的解析结果：

- 图节点、边、有序输入输出、算子标识及语义版本；
- 算子属性，包括广播对应关系、reduce axes、reshape target、transpose permutation；
- tensor dtype、shape、stride、storage offset、必要的 alias 关系；
- 动态维符号、约束、每组样本的具体尺寸；
- 权重、buffer、初始可变状态与输出结构约定。

首期允许以版本化的 NNSmith GIR 适配表示承载图，不同时发明一个完整的新编译 IR。通用元数据与加载协议必须独立于 NNSmith 内部类。

### 4.3 CaseBundle：无需落盘的不可变运行时用例

CaseBundle 表达已经确定的 CaseSpec、权重、输入样本与参考数据，不意味着必须写文件。生成器可直接返回内存对象，本机后端共享只读数据或独立重建；跨设备仅传递自包含 seed 标识即可重建 workload。

可选落盘仅用于限额临时缓存、跨进程传输或显式诊断导出，不属于默认结果归档，也不能成为复现的前提。缓存命中和缓存缺失必须产生相同 workload_id。

显式诊断导出可包含manifest、case.json、state、samples、oracles、provenance；默认不创建这些归档文件。校验缓存失败时显式报告并隔离损坏数据，不将损坏内容作为有效用例。

扩展规则：

- 新增因素不得改变旧 seed 的解释；必要时新增生成协议版本并保留旧版本实现。
- 不认识的必要语义必须拒绝，不能静默忽略。
- layout、alias 等因素必须具备对应的加载器和执行能力，不是只增加标签。
- 非连续张量按 storage 和 view 元数据重建，不能静默变连续。
- 缓存路径使用受控相对路径与内容哈希，不依赖原机器绝对路径。
- 核心语义字段结构化；扩展使用命名空间、版本和校验器。

### 4.4 ExecutionSpec 与 EvaluationSpec

ExecutionSpec：后端、设备要求、编译配置、运行选项、隔离策略。实际软件/硬件指纹单独记录。

EvaluationSpec：正确性比较规则、容差、NaN/Inf 策略、warmup、采样次数、计时口径、精度失败后是否继续测量。

改变输入 dtype/layout 等实际 workload 内容，生成新 bundle；改变后端或采样次数，不改变 workload 身份。

### 4.5 身份体系

- `experiment_id`：跨批实验集合。
- `run_id`：一次启动/续跑所属批次。
- `workload_id`：规范化图语义、状态、全部输入样本的内容指纹。
- `oracle_id`：参考结果与参考实现契约的指纹。
- `bundle_id`：冻结 bundle 内容身份，关联 workload 与 oracle；来源时间戳和文件位置不参与语义身份。
- `task_id`：一次计划执行；包含 bundle、execution、evaluation 和 repeat 身份。
- `attempt_id`：任务的一次实际尝试；重试新增记录，不覆盖历史。

seed 是生成用例的完整入口，而非数据库查找条件。workload_id 是生成结果的校验身份。相同 workload 可在多个 run 出现，属于不同观测，不自动删除重复实验。

## 5. 确定性与 input size 专项

### 5.1 seed 的稳定生成协议

目标：在无缓存、无历史文件、不同设备和不同时间的兼容运行环境中，同一 seed 标识产生相同图、广播轴、算子属性、输入规格、权重与输入字节。

```text
CaseSpec = Plan(seed_token)
Workload = Materialize(CaseSpec)
```

Plan 和 Materialize 的行为由稳定协议规定，不依赖当前后端、设备探测结果、进程历史或时间。能力检查在生成后进行；不支持的后端返回 unsupported，不能改图、改dtype或换候选后冒充同一case。

seed 标识必须包含所有会改变用例的生成语义。例如 `v1:profile-small-v1:42`（具体编码待定）自包含协议版本、不可变profile与随机载荷；原有整数seed固定映射到明确的旧协议/profile，而不是跟随最新默认值。若采用全局唯一固定profile，也可只暴露整数，但不能再允许隐藏CLI参数改变其含义。

工具升级保留旧协议实现；无法支持某版本时显式拒绝，绝不换新算法生成不同用例。自定义profile要可随标识携带或无外部查表地解码，只有一个配置哈希并不足以实现独立重建。

“相同case”要求图、输入和权重精确一致，不承诺不同后端输出位级一致。CPU oracle 的计算也可能受库版本和浮点运算影响：参考实现版本与oracle_id单独记录。若要求oracle本身跨平台位级一致，需要额外的固定参考算术协议，不能仅依赖torch的deterministic开关。

### 5.2 生成器改造：确定性优先，而非冻结旧输出替代确定性

- 首先定位广播轴漂移，建立跨进程与跨架构黄金样本；冻结已有输出只能用于诊断，不能算完成生成器重构。
- 明确PRNG算法、种子展开、字节序、整数采样和字段寻址规则，不依赖Python hash或库的隐含随机算法版本。
- 候选目录与排序属于版本化协议，禁止根据实时NPU探测和共享缓存改变候选池。
- 广播轴、rank、维度等先作确定决策，再进行约束验证。求解器有多解时必须确定唯一选择规则，不能依赖“本次返回的第一个模型”。
- 固定拒绝采样和重试顺序。超时只表示未完成，不改变后续候选选择，不接受不同部分图。
- 权重和输入采用规范化字节生成及明确dtype转换/舍入规则；浮点分布算法也须固定，不能默认不同CPU上库函数输出逐位一致。
- 现有依赖浮点梯度搜索的refine_weights、以及靠CPU执行结果选择动态候选的逻辑可能影响case身份：需替换为协议化构造/确定性校验，或采用经过跨平台验证的参考实现；不能把它们留作隐式环境依赖。
- seed重放不依赖落盘。单次实验可以只生成一次供多个后端消费，以节省成本；独立后端也必须能仅凭同一seed重建并得到相同workload_id。
- 不通过静默reshape、padding、dtype降级或改用另一个图规避不支持的情况。

### 5.3 输入一致性检查点

1. 生成完成：CaseSpec 与实际 tensor 的名称、顺序、dtype、shape、stride、alias 一致。
2. 物化或可选缓存加载：内容哈希、storage/view 边界、动态约束一致。
3. 送入后端前：使用有序 input signature 绑定，禁止各模块自行依赖字典顺序。
4. 编译产物加载：验证目标平台、后端、编译配置、代码/ABI版本与输入约束。
5. 比较输出：完整验证输出树和数量，不能使用 zip 静默漏掉输出。

动态 shape 首先考虑广播、固定权重、reshape 等约束，再用 CPU eager 验证；候选拒绝与最终运行错误分别记录。不得通过 reshape、截断或 padding 掩盖输入错误。

输入漂移定位输出预期/实际签名及首次分歧阶段；用户报告的具体广播轴与 input size 用例必须进入回归集。

## 6. 统一执行流程

所有模式复用同一实现：

```text
按seed确定性物化（或读取等价缓存）并校验 workload
 -> 后端准备 / 获取编译结果
 -> 遍历样本：执行并同步 -> 正确性检查
                         -> 可选 warmup / profiling
 -> 汇总样本与后端结果
 -> 可选后端配对比较
 -> 持久化
```

静态通常为一个样本，动态为多个样本；不是两套顶层执行器。动态 workload 复用编译 callable，但允许显式记录 guard 导致的重编译，不承诺“一次编译适用于全部 shape”。

统一结果分别表达：

- 阶段状态：成功、失败、超时、取消、能力不支持；
- 正确性：pass / fail / not_checked；
- 性能：有效 / 不可测 / 跳过，以及数值指标；
- 诊断摘要：错误阶段、错误类别和有长度上限的错误信息；完整traceback、日志与dump默认不长期保留，按seed诊断重跑时重新采集。

建议默认精度失败后继续测量以保留现有信息，但标记为精度失败；正式性能通过率与回归结论默认只使用正确性通过且可比的样本，原始 timing 仍可查询。

可变输入/状态在正确性执行和重复测量间必须按契约重置；重置是否计入时间由测量契约明确。

轻量诊断统一记录。重型 hook、dump 和失败定位使用独立诊断 attempt，不污染正式测量结果。

## 7. 并行调度与编译分离

### 7.1 调度单位

由“worker 持有完整 case”改为 case/backend 独立任务和阶段状态机：

```text
PENDING -> PREPARING -> COMPILE_READY -> DEVICE_READY -> RUNNING -> POSTPROCESS -> DONE
                  \-> FAILED / TIMED_OUT / CANCELLED / UNSUPPORTED
```

对尚不支持拆分的后端使用诚实的 `COMPILE_EXECUTE` 组合阶段，不能标记为纯 CPU 编译成功。

### 7.2 资源池

- CPU：生成、oracle、图变换、确认为设备无关的编译、统计解析。
- NPU：设备相关准备、autotune、首次执行、正确性与采样。
- 内存/磁盘：并发 token、有界队列、编译结果预算与背压。

外层编译任务数与每任务编译线程共享总预算，避免两层并发乘积导致 OOM。

每个任务是可独立调度的，但严格性能采样时同一 NPU 独占；默认配对后端在同一设备测量并平衡顺序。跨卡并行测量可用于吞吐场景，但必须记录设备差异，不自动作为严格配对性能结果。

### 7.3 后端编译能力

BackendAdapter 至少声明：

- 是否支持设备无关准备/编译；
- 是否需要设备 autotune、是否会在编译中实际执行；
- 是否支持跨进程导出/加载编译产物；
- 动态 shape、布局、alias 等支持范围。

编译产物必须绑定 workload/图约束、backend、编译选项、软件与设备目标指纹。不同进程共享缓存使用锁与原子发布，不能直接复用缺少身份校验的目录。

无法序列化 compiled callable 时，不能通过 pickle 强行移交；可保留 worker 上下文，在阶段边界等待设备租约。真正 CPU 编译拆分须有后端接口支撑。

### 7.4 恢复与故障

- 任务领取和状态更新事务化；attempt 带租约/心跳及写入代次，过期 worker 不能提交覆盖新 attempt。
- 崩溃后任务可重试，但统计只纳入明确选定的有效 attempt；不承诺外部执行 exactly-once。
- 超时终止所属进程组，不影响其他任务。
- NPU 致命异常后销毁受影响进程；设备健康检查失败则暂停该设备，不无限污染后续结果。
- checkpoint 不再埋在报告 JSON 中；数据库保存待办任务、来源配置和恢复进度。

## 8. 存储、汇总与 Web

### 8.1 轻量结果库（默认归档方式）

```text
archive/
  results.sqlite          # 唯一必需的长期结果归档

runtime/                  # 与归档分离，不随上传携带
  cache/                  # 限额编译/物化缓存，可删除并重建
  scratch/                # 当前任务临时日志与profiling文件，处理后清理
```

SQLite 默认只保存：

- 自包含seed、生成协议版本、workload指纹；
- 共享环境和执行/评估配置引用，环境/配置去重保存，不逐case重复；
- 算子、dtype、shape等查询所需的紧凑摘要与有序输入签名；
- 每后端、每shape的正确性状态、性能汇总指标、测量口径；
- 任务/attempt状态、恢复所需的紧凑元数据，以及有长度上限的错误摘要。

默认不归档模型、完整图文件、输入、权重、oracle张量、完整CaseBundle、长日志、逐次采样原始数据、完整算子统计CSV、原始profiler文件或编译产物。用例内容按seed重建，诊断细节通过重跑采集；性能数值作为历史观测必须保留，不能通过重跑替代当时结果。

建议逻辑表：experiments、runs、workloads、tasks、attempts、sample_results、environments、configs，以及本地紧凑sync_destination/sync_cursor/sync_outbox与确认状态表；另含必要的算子/dtype多值维度关联表。样本定义、图和完整bundle不再为归档目的重复存储；逐shape结果仅保存查询和比较所需摘要。

常用查询字段建索引，记录单位、统计口径和schema version。不同时保存整份summary JSON和等价拆表数据，不默认保存所有细粒度事件或无限增长的traceback。

数据库容量用代表性数据实测bytes/case（含索引、不同shape/后端/attempt数量），单独测量WAL、快照和临时缓存的峰值空间；不把未经实现验证的容量估算作为承诺。

### 8.2 写入模型

worker 返回结果或事件，主控/导入服务集中写 SQLite，短事务批量提交；UI 只读查询。使用本地磁盘和合适的 WAL 配置，不把 NFS 上共享 SQLite 当多机数据库。

只写增量结果，不在每个 case 后重写所有历史 JSON/HTML。高频展示统计可维护汇总表，但明细是事实来源，可重建汇总。

### 8.3 查询与展示

公网中心网站作为默认日常结果入口；同时支持同一pip安装包提供的按需离线快照查看模式。NPU环境不部署常驻查看Web/API，不提供SSH隧道查看流程：

- 首页数据库聚合；
- 用例列表服务端过滤、稳定排序、游标分页；
- 图表服务端聚合/分桶；
- 详情按需读取输入签名、逐shape汇总指标和错误摘要；
- 完整图、张量和诊断日志通过显式seed重放获得，不因打开页面自动启动编译或NPU任务；
- 服务端默认只展示历史结果与重放指令，不要求部署生成/执行环境，也不依赖历史大文件。

HTML 仅作为选定子集的可选静态导出，不再是默认数据库。Web依赖可放可选安装项，避免无UI环境引入整个前端链。

### 8.4 汇总规则

- 多批可展示，但环境不一致的数据按版本/设备/测量契约分组。
- speedup 必须匹配 workload、样本、设备配对策略与计时口径。
- 准确区分总任务数、有效对比数、精度失败数、生成失败数及分母。
- 重试与重复实验分别管理；不能简单按 seed 去重或平均所有 timing。
- 旧报告缺少关键字段时保留 unknown，禁止虚构指纹、版本和严格可比性。

## 9. 保留策略与服务器上传

### 9.1 默认只留结果，其余用seed重现

长期归档采用第8.1节的轻量结果库，不默认保留完整bundle，即使用例失败也不自动永久保存大文件。协议实现必须长期兼容，删除缓存不影响重建相同workload。

临时数据生命周期：

- 权重、输入和oracle：运行时物化并供后端使用，任务结束后释放。
- profiler原始文件/CSV：解析并持久化汇总指标后删除；解析失败记录短错误摘要，完整现场仅显式诊断模式保留。
- 编译/物化缓存：有容量上限、按引用安全清理，不进入结果归档或上传。
- 完整日志/traceback/dump：常规任务结束后清理；需要时按seed重跑并显式导出，导出不改变默认归档策略。
- 崩溃留下的临时目录：恢复时识别无有效任务引用的残留并清理，不能无限累积。

边界：seed重建保证workload一致，不保证重现当时设备负载、偶发故障、原始日志或逐位相同的oracle。历史指标、环境与错误摘要保留在库中；需要精确保留原现场时另行显式诊断导出。旧版非确定性生成器和无法由seed描述的外部数据不具备新协议保证，导入时标明能力，不凭空宣称可以重放。

### 9.2 上传与导入

轻量结果数据库的一致性快照 + 最小版本/校验manifest -> 校验上传 -> 服务端事务导入 -> 更新查询索引。默认不上传bundle、tensor、日志、profiler文件或编译缓存。

- 使用 SQLite backup 等一致性方式，不能只复制运行中的 WAL 主文件。
- 上传的是交换归档，不直接覆盖服务器查询库；任务恢复权限与本地租约不随报告导入接管。
- 全局ID和内容哈希保证幂等；已有运行后续追加结果可增量更新，冲突显式报告。
- 服务器界面部署一次，多批上传只更新数据。
- 服务器首期可继续使用本地 SQLite + 单写导入队列；大量并发写入出现后再迁移 PostgreSQL。

### 9.3 安全边界

- 上传有认证、TLS、容量限制和清单；默认不上传凭据、环境变量全集和任意工作目录。
- 归档解包防路径穿越、符号链接逃逸和解压炸弹；日志/图属性展示防 XSS。
- 查看服务器只解析数据，绝不在导入时反序列化执行 pickle 或运行用户模型。
- 旧 NNSmith pickle 仅在可信执行环境兼容加载；新归档优先数据化格式并记录 dtype/布局语义。
- Web读取产物通过受控ID，不开放任意绝对路径访问；中心应用监听回环/内部端口，经HTTPS反向代理提供访问；NPU环境无查看服务端口。

### 9.4 默认公网入口与近实时结果展示

每台个人NPU环境只运行测试主控、轻量SQLite与后台同步器；不部署个人Web/API、不要求用户建立SSH隧道、不提供本地连接助手。公网中心网站是默认日常结果入口；个人电脑可按需打开SQLite快照离线查看，见第9.6节。

```text
个人NPU：批测 -> 本地结果库/outbox -> 后台自动HTTPS上传
                                         |
                                         v
                                  公网中心结果库
                                         |
                                  Web / 查询API
                                         |
                                  用户浏览器
```

建议产品行为：

- 在网络和服务健康时，目标从本地结果提交到页面可见约5–10秒；这是待压测的体验目标，不是已验证SLA。客户端通常每2–5秒或达到批量阈值同步，页面每2–5秒增量查询，任务结束时触发最终同步。
- 状态/心跳限频同步，历史积压分批回填；不得因频繁显示进度拖慢NPU测试。
- 网站显示最后同步时间、来源在线/离线状态和数据新鲜度；失联不代表测试失败或完成。
- 唯一导航为“总览 -> 我的/团队批次 -> 用例 -> 后端/各shape结果”；URL保留筛选条件，便于分享与收藏。
- 完整列表服务端分页，首页/图表服务端聚合，单条详情按需加载。
- 中心不可达时，测试和本地结果保存继续，恢复后自动补传；离线期间可用CLI查看运行与同步状态；已导出的SQLite快照可在个人电脑离线查看，不在NPU环境增加常驻Web服务。
- 同步器由可用进程管理器托管，不能假设容器支持systemd；工具启动时幂等确保服务运行。

此前在`npussh mlir`做过回环HTTP与SSH转发探针且已退出；它只证明该访问方式技术可行，不再作为本方案交付功能。中心公网HTTPS出站连通性仍需部署时逐环境验证。

### 9.5 公网汇总：客户端主动上传，不由服务器连接NPU

```text
个人NPU A：结果库/outbox -> 后台同步器 --HTTPS--+
个人NPU B：结果库/outbox -> 后台同步器 --HTTPS--+-> 公网IPv4服务器
个人NPU C：结果库/outbox -> 后台同步器 --HTTPS--+     反向代理/TLS
                                                 -> 认证上传API
                                                 -> 串行导入 -> 汇总SQLite
                                                 -> 同源Web/只读查询API
```

NPU仅需出站HTTPS，无需公网IP、入站端口或被服务器SSH登录。若某个环境无法直接访问服务器，允许导出轻量交换包到个人电脑，由相同publish客户端上传。公网服务器只做数据服务，不需要NPU、torch或模型执行权限。

推荐公网IPv4配域名及有效TLS证书，使用Caddy/Nginx终止TLS，应用监听回环/容器内部端口，对外仅开放必要HTTPS入口。不依赖纯HTTP传输token。仅有IP也需解决受客户端信任的证书或私网安全隧道，不能关闭TLS校验。

首次配置后自动同步（拟议功能，尚未实现）：

1. 管理员离线创建用户、分配唯一展示名并安全分发个人上传密钥；首期不提供在线注册、密钥申请/发放或自助找回接口。首次setup只配置服务器、管理员给定的展示名和密钥，服务器地址可预置；密钥隐藏输入，不写命令行、shell history、结果库、日志或上传包。
2. setup调用认证/配置校验接口，仅核对已预置身份与展示名，返回稳定owner_id，不创建用户或签发密钥；未知密钥/身份不匹配时明确提示联系管理员。展示名仅用于显示和筛选，不用于鉴权、数据主键或同步游标。管理员维护全局唯一性；改名不改变归属。每人独立密钥，撤销/轮换同样由管理员离线操作，不使用共享团队密钥冒充个人认证。
3. 本地生成稳定source_id，经已有密钥授权登记到该owner（设备来源登记不等于用户注册或密钥发放）；同一用户多台环境使用不同source_id。克隆正在使用的数据库/配置到另一台机器时必须重新登记来源，防止两个写入者使用同一序号流。
4. setup启用工具本身的后台同步服务。结果提交后自动进入待同步集合，按时间/条数合并上传；服务重启后自动续传，不需要每个run手动publish或保持浏览器打开。
5. 同步服务与批测分离，由可用进程管理器自动重启和启动。容器无法开机自启时，工具启动需幂等确保服务运行；不能承诺环境关机或服务未运行时仍可上传。测试结束后服务继续补传积压。
6. 网络失败指数退避并加入抖动；上传故障不阻塞批测。401/403等凭据错误进入blocked状态，明确显示需修复，不能无限快速重试。轮换密钥不丢失进度，不改变owner/source。

本地必须持久化同步进度，不能只在进程内保存一个“已上传”标记：

- `sync_destination`：服务器标识、owner_id、source_id、服务端数据集epoch及最后成功时间；密钥仅保存于OS凭据存储或权限0600的独立配置文件。
- `sync_cursor`：每个服务器/来源的已确认连续change_seq、当前批次范围/ID、重试次数、下次重试时间、最近错误及同步状态。
- `sync_outbox`：实体类型、实体ID、待同步revision和change_seq。与结果变更在同一本地事务中提交，避免结果写入成功但遗漏待上传标记；不重复存整份结果/tensor。
- 对实体保留每个目的地的acked_revision，用于UI准确区分“未上传”“上传中”“已同步”“已同步但有更新待上传”“重试等待”“同步受阻”。“已同步”仅指当前revision被服务端确认，不是这个case以后永远无需上传。
- uploader在一致性读事务中组装批次，网络请求在事务外执行；保留有界in-flight批次内容/校验以安全重发，不能拿同一个batch_id发送变化后的payload。
- 服务端确认后，本地短事务推进游标和acked_revision；若实体在上传期间又有新revision，旧ACK不能将其标记为最新已同步或删除新待办。
- 已确认outbox与批次临时内容及时压缩/清理；尚未确认的最终结果不能因日志保留期丢失。状态更新允许按规则合并为最新revision，但attempt与历史测量记录不可被合并删除。
- 中心数据集epoch改变或游标基线丢失时进行握手核对，从轻量结果库重新做快照同步，不能盲信旧的本地“全部已上传”。

上传协议：

- 默认按版本化增量记录持续同步；首次接入、大量历史回填或游标过旧使用一致性轻量SQLite快照建立基线，不每次复制整个库。
- 请求包含source_id、run_id、schema_version、revision范围、batch_id和内容校验。中心从上传密钥确定owner并检查source归属，不能信任客户端自报用户名。
- 首期每个来源/目的地只允许一个上传者，使用本地锁/租约避免多进程重复调度；中心仍必须支持幂等接收。
- 中心校验并事务提交整批后才确认；ACK返回已接受批次和连续序号/实体revision。存在缺口不能把最大序号当成全部已收到，部分失败不推进越过缺口的游标。
- 断线、ACK丢失、服务端提交后本地崩溃均可重发；相同batch_id不同内容拒绝，迟到旧revision不能覆盖新数据。
- attempt保留原身份；服务器不按seed去重不同人的观测，也不把重复上传算成新实验。
- 同步仅包含第8.1节白名单字段，不包含同步密钥、本地sync表/租约、绝对路径、tensor或编译缓存。普通快照同步与断点恢复是不同职责。
- 限制上传大小、速率、协议版本；快照只解析白名单schema，不执行来源数据库内的任意SQL，也不将其替换为服务器工作库。

本地通过`autofusedbg fuzz sync status`显示：服务器、展示名、后台服务状态、最后确认时间、积压数量、各run已同步/未同步/待更新数量及最近错误；CLI可列出待上传记录；中心展示最后一次收到的同步摘要，不能在来源离线时声称知道最新本地积压。任务计数和上传状态独立，例如“测试完成，但仍有12条结果待同步”。手动重试/导出保留为诊断入口，不是日常必需操作。

中心展示：

- 首页按成员、run、代码/环境版本、时间、设备、算子、dtype和shape筛选。
- 默认展示团队总览和成员入口；成员身份与访问权限由服务器管理。上传凭据只能修改自己的来源，浏览使用管理员离线开通的只读身份及独立登录会话；页面不提供注册/密钥申请入口，不使用上传密钥作为浏览器登录凭据。浏览凭据也由管理员离线分发，不把个人上传token嵌入页面。
- seed与workload指纹用于定位相同测试负载；跨设备结果分组展示，不能直接混算严格speedup。
- 显示最后同步时间和运行方报告状态。离线/同步滞后不等于任务失败，浏览器不得自行把过期“running”标记为完成。
- 默认不匿名公开数据；若需公共只读分享，使用明确发布范围、脱敏及可撤销访问策略。

首期中心SQLite采用单写导入队列、本地磁盘、备份与只读查询即可；成员数量本身不是迁移依据，以导入延迟、写锁竞争和查询负载决定是否升级PostgreSQL。

尚待部署验证：公网服务器地址/域名、TLS、容量和认证方式，以及每个NPU环境的出站连通性。当前未提供中心服务器，尚未验证或部署中心服务。

### 9.6 统一pip安装与离线SQLite查看

采用与autofusedbg相同的Python/pip分发方式和同一个autofusedebugger安装包，不额外维护npm包、Electron应用或每种操作系统独立安装器。Windows、macOS、Linux复用同一份Python实现和预构建Web静态资源；仍需跨系统CI验证，不承诺无需测试即可兼容。

拟议使用方式（尚未实现，现有发布版本不具备以下新命令）：

```bash
python -m pip install autofusedebugger
# 系统Python限制直接安装时，使用venv或pipx隔离安装，不要求管理员权限。
autofusedbg fuzz view ./results.sqlite
```

安装包和依赖边界：

- 基础安装直接提供查看器和CLI，使用Python标准库sqlite3读取数据库；Web静态资源在发布时构建并随wheel分发，用户不需要Node.js、前端构建工具或网络CDN。
- 不依赖独立SQLite服务、Torch、torch_npu、NNSmith或CANN即可查看快照。测试运行依赖由显式运行环境准备流程配置，不能因安装查看器自动下载或替换现有Torch/NPU栈。
- 必须移除包顶层import引发的环境变量修改、NNSmith补丁和重型依赖加载；查看器不能仅在CLI分支延迟导入，却仍触发顶层初始化副作用。
- 查看器、中心服务共享只读查询/统计层和前端资源；上传、认证、写入等中心功能按运行模式启用，本地查看模式不启动这些功能。
- Python最低版本和SQLite功能基线在发布时明确；使用同一版本号和schema兼容矩阵，不维护查看器独立版本线。

运行行为：

- `fuzz view <文件>`不需要setup、上传密钥或NPU环境；只读打开指定快照，自动选择空闲回环端口并尝试打开浏览器，失败时输出URL。支持`--no-open`和显式端口。
- 仅监听127.0.0.1；限制Host/Origin并使用本地访问会话防止其他网站滥用本机API。不允许任意路径读取或执行来源数据库的SQL/扩展，不启动自动同步、测试或用例生成。
- 页面提供与中心相同的分页、筛选、汇总和逐case详情；关闭服务后退出。所有资源本地提供，安装完成后查看可完全离线。
- 不自动迁移/写回用户快照；支持已声明的旧schema只读适配，新版本schema不兼容时提示升级。损坏或不完整快照明确报错。

安全快照与更新：

```bash
# 在NPU环境生成一致性单文件快照（剔除本地同步/租约元数据，仅保留展示白名单）
autofusedbg fuzz snapshot --out ./results-view.sqlite
# 复制快照到个人电脑后
# 首版：停止查看器 -> 完整复制/替换快照 -> 重新运行view
```

snapshot使用SQLite backup等一致性机制并导出展示数据，不能只复制正在写入的WAL主文件。快照不含上传密钥，分享意味着接收者可读取其中全部结果，需提示环境信息披露范围。

首版不承诺热替换；后续如提供“打开新快照/刷新”，需先完成临时文件复制与校验，再关闭旧连接切换，避免读取半文件或长期持有旧库。SQLite文件是完整展示数据来源，输入/权重仍按seed在具备执行环境的机器重建。

验收：三个系统在不安装Torch/NNSmith/NPU依赖的干净Python环境中，通过同一个wheel安装并离线打开快照；无额外编译步骤；查询结果与中心一致；原库只读不变；snapshot覆盖运行中WAL、旧schema和损坏文件测试。

### 9.7 中心服务简单部署与迁移（交付硬要求）

- 一个应用包含API、后台导入和预构建Web；SQLite落在单独持久化目录。首期单应用实例/集中写，不依赖Redis、PostgreSQL、独立前端构建服务或NPU运行环境。
- 主部署路径提供版本固定的Docker Compose：应用加可选TLS代理。配置域名、数据路径和必要端口后，`docker compose up -d`启动；已有HTTPS网关时只部署应用。提供linux/amd64与linux/arm64镜像并测试，不在用户服务器现场编译前端。
- 无Docker环境提供相同pip包的服务启动入口与进程管理示例，复用同一实现，不另建功能不同的服务版本。具体server命令在实现时定型。
- 配置与状态分离：镜像/安装包不可变，业务库、预置身份/密钥验证记录、同步批次确认记录等持久化状态集中管理，外部地址不写死在结果记录或产物中。
- 管理员离线CLI负责初始化、用户/密钥管理、备份和恢复；不提供在线注册或密钥申请。上传密钥服务端保存安全验证值，不保存可随报告导出的明文；会话签名等服务秘密独立受限存储。
- 提供健康检查、schema版本检查、磁盘容量提示及限额运行日志；容器重启后恢复服务，但绝不自动派发NPU任务。
- 一条备份命令生成可恢复包：一致性SQLite备份、部署配置、身份与同步元数据；秘密配置单独安全备份，不混入可分享的结果快照。备份含manifest和版本信息。
- 迁移流程：预备份验证 -> 暂停旧服务接收写入 -> 最终一致性备份 -> 传到新环境 -> 同版本恢复启动 -> 切换域名/入口 -> 验证客户端继续同步。旧服务停写后才能完成切换，不能两端独立接收同一来源后再覆盖数据库。
- 保留owner/source/批次幂等身份；恢复过期备份后轮换服务端同步epoch，让客户端重新核对/补传，不能因本地旧ACK造成缺失。正常域名切换无需用户重新setup；地址改变时允许一次受控配置更新，不能绕过TLS校验。
- 升级前一致性备份，明确数据库迁移与回滚策略；不能用旧程序直接打开已升级且不兼容的schema。首版维护期间允许短暂中断，客户端本地排队自动补传。

验收：干净服务器按发布说明启动，无需源码编辑和手工建表；第二个环境按备份恢复后，用户归属、历史结果和同步恢复正确。部署/迁移步骤、停写窗口及可回滚条件均实测记录，不能只提供理论命令。

## 10. 代码组织建议

不一次性搬迁整个项目，先在现有入口背后引入以下职责：

```text
af_fuzz/
  contracts/       用例、执行、评估、结果、版本契约
  generation/      规划、因素策略、确定性物化
  adapters/        NNSmith、AscendC、Triton等适配
  execution/       公共执行器、正确性、profiling、诊断
  orchestration/   任务状态、资源租约、超时、恢复
  storage/         轻量SQLite、限额临时缓存、迁移、结果归档
  reporting/       查询聚合、导出
  web/             API及按需加载界面
```

目录名在实施时确定；关键是依赖方向而非提前创建所有空模块。

NNSmith 补丁从普通 import 副作用迁至显式 prepare/doctor；并发运行前完成准备和版本校验，避免多个 worker 修改同一依赖安装。旧启动方式提供明确迁移提示。

## 11. CLI 与兼容策略

统一使用短子命令`fuzz`，完整入口为`autofusedbg fuzz ...`（长可执行名`autofusedebugger`仍可使用）。文档、页面复制命令和帮助均使用新名称；旧`af-fuzz`仅在迁移期作兼容别名并提示弃用，不维护第二套实现。以下命令为拟议功能，尚未实现：

```text
首次配置：autofusedbg fuzz setup       # 离线发放的展示名/密钥，服务器可预置
生成/执行：autofusedbg fuzz run ...
重放：    autofusedbg fuzz replay --seed <seed_token> ...
运行状态：autofusedbg fuzz status
同步状态：autofusedbg fuzz sync status # 后台自动上传，无需逐批操作
旧数据：  autofusedbg fuzz import --source <summary.json或目录>
诊断导出：autofusedbg fuzz export --format json|csv|html ...
手动补救：autofusedbg fuzz publish ...
查看结果：打开公网中心网站（默认入口）
导出快照：autofusedbg fuzz snapshot --out ./results-view.sqlite
离线查看：autofusedbg fuzz view ./results-view.sqlite # 同一pip安装包，无需NPU依赖
```

NPU环境不提供常驻`serve`或SSH查看助手；个人电脑通过`view`按需只读查看快照。结果库位置由首次setup确定，日常命令无需重复指定；保留显式覆盖数据目录的高级选项。静态导出仅作诊断/数据交换，不作为第二套日常查看系统。

`--repro-seed` 是主重放入口，直接按seed标识解码协议和profile，确定性生成，不要求查数据库或下载bundle。任何改变生成语义的参数必须产生不同seed标识，或在重放时拒绝冲突参数。旧版裸seed按兼容策略明确区分，不冒充新协议保证。

旧 summary.json 导入后保留来源路径/哈希，报告可查看；缺少 case 数据不能自动变成可重放 bundle。旧 checkpoint 不能未经转换作为新调度器任务状态。

## 12. 实施阶段与验收

### P0：行为基线与故障定位

- 收集用户广播轴漂移、input size 故障的具体 seed、配置、版本和日志。
- 记录原始图、输入签名、候选池与完整错误阶段，建立回归集。
- 补齐可工作的双后端验证环境；测量生成、编译、设备准备、执行、报告阶段成本。
- 验证编译产物边界，输出后端 split / combined 能力矩阵。

验收：已知故障可稳定复现或清楚标记尚缺证据；不以新架构替代根因定位。

### P1：确定性生成协议与统一执行

- 引入稳定seed协议、CaseSpec/CaseBundle、规范化内容身份和输入签名校验。
- 实现无缓存确定性物化；同次运行可共享，跨设备可独立生成；各模式共享执行实现。
- 固定已知不确定因素，移除执行时隐式生成和补丁修改。

验收：删除全部缓存和历史数据库，仅用相同seed，在不同设备、受支持CPU架构、进程、worker数量和时间独立生成，CaseSpec和输入/权重字节指纹一致，广播轴不变；工具升级后旧seed黄金样本不变；不支持设备返回unsupported而不改case；oracle版本差异单独报告。

### P2：数据库与按需 Web

- 增量结果、独立checkpoint、旧报告导入、跨批查询和分页界面。
- 默认停止全量HTML重写；只归档轻量结果，提供子集导出与临时文件/限额缓存清理。

验收：归档不包含模型/tensor/profiler/编译产物/长日志；无缓存seed重建通过；任务完成及崩溃恢复后临时目录可清理；实测每case数据库空间；重复导入无重复计数；重试与重复实验可区分；十万级合成结果不全量进入浏览器，分页大小固定，首页和查询时间记录并与旧实现对比。最终延迟预算按部署硬件基线确定。

### P3：阶段调度与性能优化

- 任务拆为 case/backend，CPU池与设备租约分离，有界队列和背压。
- 对验证支持的后端启用 split；不支持的保留显式 combined 模式。
- 记录 CPU队列、编译、设备等待、autotune、执行、profiling、后处理耗时。

验收：CPU编译与其他任务NPU执行确实重叠；性能设备独占；相同工作负载下吞吐、峰值RSS、磁盘和测量稳定性可对比，不承诺未经实测的倍数提升。

### P4：归档发布与回归管理

- 默认公网Web入口及同一pip包离线快照查看；管理员离线预置用户和分发密钥、首次配置校验、持久化outbox与CLI同步状态、中心HTTPS近实时自动上传、认证归属、幂等导入、增量同步、环境分组与跨版本回归。

验收：仅上传轻量结果与校验清单；中断上传、重复上传、运行中快照、恶意路径、快照损坏均有测试；服务器导入不执行模型；断线重传、ACK丢失、本地重启、上传中新增revision、密钥失效/轮换、中心epoch变化、跨用户越权有测试；同步不阻塞批测；跨版本性能配对规则可解释。

## 13. 测试矩阵

- 契约：schema迁移、规范化哈希、未知必要字段、文件损坏、路径安全、alias/stride重建。
- 确定性：不同进程、hash seed、CPU线程数、前序随机历史、worker数量、冷暖缓存；比较具体轴与图属性，而不只检查seed相等。
- 动态：广播、固定权重、reshape约束、合法与非法变体、逐shape输出和guard重编译记录。
- 执行：后端异常、输出数不一致、精度失败继续测量、可变输入重置、诊断不污染采样。
- 调度：超时、worker崩溃、父进程退出、设备异常、租约过期、重复提交、磁盘不足、背压。
- 数据：事务中断、恢复、重复导入、旧schema、缺环境字段、跨批统计分母和配对条件。
- 性能：相同固定bundle集合、相同设备与编译配置，对比端到端吞吐及资源开销；冷暖编译缓存分别测量。
- 安全：数据导入不触发反序列化执行、XSS、路径穿越和越权产物访问。

## 14. 主要风险与待确认项

1. 用户报告的 seed 广播轴漂移与 input size 故障尚未完整定位；必须有具体回归用例。
2. 两个后端能否提供端到端编译/执行分离接口，尤其动态图和autotune，仍需验证。
3. 跨架构字节一致生成与长期协议维护成本：必须固定算法并保留旧实现，不能以本机少量测试代替跨设备验收。
4. 既有输出消费者、CLI和checkpoint的兼容需求需盘点；通过导出和迁移适配，而不是长期维护两个执行引擎。
5. 首期Web框架与部署方式在实现阶段选择，保持轻量；不提前引入分布式基础设施。

建议评审确认的默认决策：seed驱动跨设备/时间的确定性生成，CaseBundle无需强制落盘；SQLite仅归档轻量结果，其余按seed重建；公网默认入口及近实时同步、同一pip包按需离线查看；用户/密钥离线开通；统一`autofusedbg fuzz`命令；后端任务独立调度；严格计时NPU独占；精度与性能结果独立；完整bundle不默认归档，仅作限额临时缓存或显式诊断导出。
